## 一、需求与边界

### 1.1 用户诉求（原始表述）

- 保留原有项目的前提下，把财务相关功能集成到个人工作台；
- 结合 GitHub 上"上手难度小、效果好"的 **MIT 协议**开源项目；
- 让工作台更适合自己，**要求模块化**；
- 技术架构与实现由 AI 决定。

### 1.2 硬性约束（与既有架构评审对齐，不可违反）

| 约束 | 来源 | 本方案的遵守方式 |
|------|------|----------------|
| 不做"重写式统一平台"（评审已三次否决，40-80 人日不可回收） | 架构评审报告 2026-10-01 | 只做**宿主 + 薄模块**，引擎内核零改动 |
| 现金流 V1 含真实业务数据，**永不推远端** | 仓内数据安全声明 | 模块仅本机引用其引擎，数据文件不出本机 |
| 真实业务值（公司名/账号/内网地址）外置 | 各仓 local_business.json / config.local.yaml 约定 | 模块通过**只读引用**原配置加载链，不复制、不另建真值副本 |
| 工作台仅监听 127.0.0.1、无鉴权、SQLite 单文件、不用 Docker | workbench spec | 全部模块遵守；新增监听/端口一律禁止 |
| 删除类操作不开放给 Agent | workbench agents/tools.py 设计决策 | 财务模块注册的 Agent 工具同样只开放查询/创建类 |

### 1.3 现状关键事实（2026-10-12 调研结论）

- 工作台**业务层是硬编码分层架构**：加一类新实体要改 8 处（model+schema+router+tools 注册+前端 view+router+菜单+仪表盘聚合），**没有模块机制**——这是集成前必须先补的能力。
- 工作台 **Agent 层已是数据驱动**（专家/模型/技能/插件四件事都可配置），模块化基础好。
- 财务资产分布在 10 个项目里，成熟度差异大：企业所得税计算已是 FastAPI+React 的 Web 应用；费用分类引擎已产品化（规则外置单一权威源）；发票工具的 PDF 提取是纯函数；现金流/POS/税金底稿是重业务脚本+exe；FSSC 是重浏览器自动化。

## 二、总体架构：Module Registry（模块注册器）

### 2.1 设计决策

不做微服务、不引入新进程、不换技术栈。在工作台现有 FastAPI + Vue3 骨架上，**各加一个"目录扫描式模块加载器"**，把"新增业务实体要改 8 处"降为"新建一个目录"。

```
┌─────────────────────────────────────────────────────────┐
│  personal-workbench（宿主，保持不变的核心）                  │
│  ├─ 任务 / 日程 / 笔记 / 概览 / 全局搜索 / AI 助手 / 定时任务   │
│  └─ Module Registry（新增）                                │
│       ├─ 后端: app/modules/ 目录扫描 → 动态 include_router   │
│       └─ 前端: src/modules/ glob 扫描 → 动态路由 + 菜单数据驱动 │
├─────────────────────────────────────────────────────────┤
│  财务模块群（每个 = 一个目录，可独立增删，互不调内部实现）         │
│  finance-invoice   发票处理（L0 直挂引擎）                    │
│  finance-expense   费用分类汇总（L0 直挂引擎）                 │
│  finance-tax       企业所得税（L0+ 整体并入）                  │
│  finance-cashflow  现金流填报（L1 任务型薄壳）                  │
│  finance-pos       POS 对账（L1 任务型薄壳）                   │
│  finance-board     微信报表看板（L2 产物嵌入）                  │
│  finance-vault     DuckDB 数据仓（可选底座模块）               │
├─────────────────────────────────────────────────────────┤
│  原项目（全部保留原位、独立可运行，模块只读复用其引擎）             │
│  FSSC平台 / 发票工具 / 企业所得税 / 现金流V1 / 费用分类v2.0 / ... │
└─────────────────────────────────────────────────────────┘
```

### 2.2 四级接入策略（核心决策）

| 级别 | 含义 | 适用对象 | 工作量 |
|------|------|---------|--------|
| **L0 纯函数直挂** | `import` 原项目引擎（纯 Python、无 GUI 耦合），包一层 router + schema | 发票提取、费用分类、税额计算 | 小 |
| **L1 任务型薄壳** | 不重写引擎，包装为"上传输入文件 → 后台执行原脚本 → 产物入库供下载" | 现金流 V1、POS 对账、税金底稿 v6.2、收入确认排版 | 中 |
| **L2 产物聚合** | 只接产物不接过程：静态托管/iframe 嵌入，或登记 exe 入口 | FSSC 平台 exe、微信报表 HTML 看板 | 很小 |
| **L3 仅登记** | 文档/手册类只在资料库建索引 | 美债投资合规手册 | 忽略 |

### 2.3 后端模块机制

**目录约定**（新增 `backend/app/modules/`）：

```
backend/app/modules/
├── __init__.py            # ModuleRegistry：扫描子目录 → 校验 manifest → 挂载
├── _template/             # 模块模板（复制即新模块）
│   ├── manifest.py        # 模块自描述（唯一强制文件）
│   ├── router.py          # APIRouter，prefix 由 manifest 声明
│   ├── models.py          # SQLAlchemy 表，表名强制 mod_<name>_* 前缀
│   ├── schemas.py         # Pydantic v2
│   └── service.py         # 业务逻辑 / 对原项目引擎的 import 封装
└── finance_invoice/ ...
```

**manifest.py 规格**（模块唯一契约）：

```python
# backend/app/modules/finance_invoice/manifest.py
from app.modules.spec import ModuleManifest, AgentToolSpec

MODULE = ModuleManifest(
    name="finance_invoice",            # 目录名，全局唯一
    title="发票处理",
    version="0.1.0",
    prefix="/api/finance/invoice",     # 强制 /api/finance/ 命名空间
    tables=["mod_invoice_batch", "mod_invoice_item"],
    menu={"group": "财务", "icon": "Tickets", "order": 10},
    agent_tools=[                      # 可选：自动注册进 Agent 工具白名单（仅查询/创建类）
        AgentToolSpec("invoice_list_batches", "查询发票处理批次", readonly=True),
    ],
    requires=[],                       # 依赖的其他模块名
    enabled=True,
)
```

**加载器行为**（`ModuleRegistry.load(app, engine)`）：
1. 扫描 `app/modules/*/manifest.py`，校验 name 唯一、prefix 以 `/api/finance/` 开头、表名以 `mod_<name>_` 开头；
2. `include_router(module.router, prefix=manifest.prefix)`；
3. 模块 models 并入 `Base.metadata`，走现有 `create_all` + PRAGMA 轻量补列（**不引入 Alembic**，与工作台现有惯例一致；表结构复杂变更靠模块版本号 + 手工迁移函数）；
4. manifest 声明的 `agent_tools` 注册进现有 `agents/tools.py` 的白名单机制，专家团队（可新增"财税专员"专家）即可调用；
5. 任一模块加载失败 → 记录错误并跳过，**不影响宿主与其他模块启动**（模块即插件，故障域隔离）。

**文件存取约定**：统一 `backend/data/finance/<module>/inbox|outbox|tmp` 三级目录；上传沿用现有附件的路径防穿越与大小限制；产物下载走流式响应，文件名 RFC5987 编码（中文名）。

### 2.4 前端模块机制

**目录约定**（新增 `frontend/src/modules/`）：

```
frontend/src/modules/
├── index.js               # import.meta.glob('./*/manifest.js') 自动发现
└── finance-invoice/
    ├── manifest.js        # { name, title, icon, group:'财务', routes:[{path, component}] }
    └── views/
        ├── BatchList.vue
        └── BatchDetail.vue
```

- `router/index.js`：保留现有 6 条静态路由，追加 `modules/index.js` 收集的动态路由（`router.addRoute`，统一 `/finance/xxx` 路径段，懒加载）；
- `AppLayout.vue`：菜单改为数据驱动——静态菜单组 + "财务"模块菜单组（按 manifest 的 group/order 聚合排序），**现有 6 页代码一行不改**；
- 组件库继续用 Element Plus；重表格场景引入 AG Grid Community（见选型节）；
- 模块内复用现有 `api/index.js` axios 封装（统一中文报错）与 `utils/` 工具。

## 三、财务模块逐个设计

> 每个模块给出：来源项目 → 接入级别 → 复用内容 → API 草案 → 前端页面 → 数据表 → 验收标准。

### 3.1 finance-invoice 发票处理（P1，L0）

- **来源**：`01-财税自动化/发票工具/发票批量重命名增加项目/invoice_processor`
- **复用**：`src/pdf_processor.py`（数电发票 PDF 文本提取 + 正则字段解析，纯函数）、`invoice_processor.py` 的冲红配对/去重逻辑、`config_manager.py` 的 yaml 配置合并
- **形态**：上传发票 ZIP/多 PDF → 逐张解析（购方/销方/金额/税率/发票号/开票日期/专普票）→ 列表可编辑 → 按规则重命名 + 按项目归档 → 生成 Excel 清单 → 打包 ZIP 下载
- **API 草案**：
  - `POST /api/finance/invoice/batches`（multipart 上传，建批次，后台解析）
  - `GET /api/finance/invoice/batches` / `/{id}`（批次与明细）
  - `PATCH /api/finance/invoice/items/{id}`（人工修正字段/项目归类）
  - `POST /api/finance/invoice/batches/{id}/export`（执行重命名+归档+出清单，返回任务 id）
  - `GET /api/finance/invoice/batches/{id}/download`（ZIP 下载）
- **前端**：批次列表页（AG Grid）+ 批次详情页（明细表格 + 行内编辑 + 导出按钮 + 产物下载）
- **表**：`mod_invoice_batch`（状态机：uploaded→parsed→exported）、`mod_invoice_item`（发票字段 + 冲红配对指针）
- **注意**：仅支持文本型 PDF（原引擎限制）；扫描件提示走人工。真实地址关键词等仍读发票工具的 `config.local.yaml`，**只读引用**
- **验收**：68 个原测试不受影响；上传 10 张混合发票 ZIP 能解析→编辑→导出 ZIP，台账 xlsx 可打开

### 3.2 finance-expense 费用分类汇总（P1，L0）

- **来源**：`01-财税自动化/现金流滚动预测/费用分类汇总系统-v2.0/`
- **复用**：`expense_classification.py` 分类引擎 + `classification_rules.json`（**单一权威源，与现金流 V1 共享**，模块只读引用，不复制）+ `rules_loader.py`
- **形态**：上传银行明细账/凭证列表 xlsx → 20/28 类费用自动分类 → 规则命中/未命中分栏 → 汇总报表（ECharts 饼图/趋势）→ 下载结果 xlsx
- **API 草案**：`POST /rules/reload`、`POST /classify`（上传即分类）、`GET /runs/{id}`、`GET /runs/{id}/report`、`GET /rules/summary`
- **前端**：上传向导页（文件→字段映射确认→执行）+ 结果页（分类汇总表 + 图表 + 未命中清单供人工归口）
- **表**：`mod_expense_run`、`mod_expense_row`（未命中行落库，便于规则迭代）
- **价值**：这是全库"规则数据化"最成熟的资产（GitHub 已开源 MIT），先做它可把模块机制趟通
- **验收**：用 v2.0 自带样例数据对拍，模块分类结果与原 CLI 输出逐行一致

### 3.3 finance-tax 企业所得税（P2，L0+ 整体并入）

- **来源**：`01-财税自动化/企业所得税计算/企业所得税计算/`（本身已是 FastAPI + React + SQLite）
- **复用**：`backend/services/tax_calculator.py` 税额计算引擎 + `calc_rules.py`（按"年份+政策文件"可插拔，评审认定的正确设计）——**零改动 import**；routers/services 整体改造为模块目录
- **前端**：React 页面**用 Vue3 + Element Plus 重写**（工作量主要在这里；申报表/纳税调整明细两个表单页 + 企业管理页 + 申报列表页）。过渡期可 iframe 嵌入原 5173 页面，但正式版应重写以统一体验
- **API**：平移原 routers 到 `/api/finance/tax/...`
- **表**：沿用原表结构，改名加 `mod_tax_` 前缀，写一次性数据导入脚本（原 SQLite → 工作台库）
- **验收**：974 个原测试中引擎相关用例在模块内保持全绿；E2E 冒烟 8/8 场景在模块版复现

### 3.4 finance-cashflow 现金流填报（P3，L1 任务型薄壳）

- **来源**：`现金流滚动预测/现金流滚动预测表自动化填报/V1/`（**永不推远端**，模块仅本机存在，不进 GitHub）
- **形态**：不重写 2400 行的 `cashflow_autofill.py`。工作台做"填报任务"页：选择/上传 5~7 份输入 xlsx → 调原引擎（子进程或 import）执行 → 展示填报报告 md + 桥接对账差异 → 下载已填报模板/取数复核 xlsx
- **共享规则**：继续只读 `rules_shared/classification_rules.json` 权威源
- **表**：`mod_cashflow_run`（输入清单 JSON、执行状态、产物路径、差异摘要 JSON）
- **安全**：整个模块的目录与产物在 `.gitignore` 声明排除（与 V1 现有声明一致）
- **验收**：用 10-08 A/B 基线数据跑一轮，产物与 exe 版输出一致

### 3.5 finance-pos POS 对账（P3，L1）

- **来源**：`收款认领POS台账/`（四源交叉对账）
- **形态**：同 L1 模式——上传 4 份输入（SHOP 对账单 zip/认领记录/辅助明细账/凭证列表）→ 后台执行 → 7 Sheet 差异分析 xlsx + 合并 PDF 下载
- **表**：`mod_pos_run`
- **验收**：用仓内 8 月工作日志对应的历史输入复跑，差异分析结论一致

### 3.6 finance-board 微信报表看板（P2，L2 产物嵌入）

- **来源**：`微信报表监控/`（扫描→抽取→脱敏→单文件 HTML 看板，管线已是 m01→m04）
- **形态**：管线保留为脚本，由工作台**定时 Agent 调度**（每天/每周自动跑）；最新 HTML 产物在工作台"经营看板"页内嵌展示（静态托管 + iframe），历史看板列表可追溯
- **脱敏**：沿用其 `masking.py`（种子映射 + 长键优先替换 + PII 正则），看板只展示脱敏版
- **表**：`mod_board_snapshot`（快照时间、来源文件数、产物路径）
- **验收**：定时任务触发后看板自动更新；来源文件数统计（331 个口径）与现版一致

### 3.7 finance-vault 数据仓（P3，可选底座）

- **来源**：`本地数据仓库/`（DuckDB，dw_core 全中文模块）
- **形态**：作为模块内嵌 DuckDB 文件（`data/finance/vault/vault.duckdb`），其他财务模块的产出（发票明细、分类结果、税额记录）可选同步入仓；提供只读 SQL 查询 API（白名单表 + 行数上限 + 超时）给看板页和 Agent 用
- **价值**：让 AI 助手能直接回答"上月费用分类汇总""某项目发票总额"这类跨模块问题
- **验收**：入仓/查询 API 测试；Agent 通过工具完成一次跨表问答

### 3.8 FSSC 平台与收入确认排版（L2/L3，不做模块）

- FSSC：重浏览器自动化 + 断点续跑 + exe 分发，**不塞进 Web 进程**。工作台仅在其"资源/工具箱"区登记 exe 入口与产物目录说明；远期可把产出台账 xlsx 导入 finance-vault
- 收入确认附件整理：Excel COM 依赖重，保留桌面 exe，同上登记入口
- 美债投资合规手册：文档进资料索引（L3）

## 七、与既有架构评审的口径对齐声明

10-01 三轮评审否决的是"重写所有工具、统一后端的 40-80 人日平台化"，并认定"1 平台 + N 独立工具 + fslibs 薄共享 + 规则数据化"为正确形态。本方案是该结论的延续：不重写任何引擎、不迁移任何数据真值、故障域各自独立；只是把"统一入口"这一收益通过模块机制拿到手。若未来出现多人协作/SaaS 化需求，应按评审预留的翻案条件重新评估，而不是在本方案上继续堆叠。
